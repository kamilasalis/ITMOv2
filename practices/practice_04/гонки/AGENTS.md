# AGENTS.md

Инструкции для AI-агента (Claude Code), работающего над проектом **«Гонки»**.

## О проекте

Учебный проект в рамках практики по работе с AI-агентами. Цель практики — реализовать
две маленькие фичи на примере AI-review API, перенеся тот же подход на свою систему.

## Стек

- **Бэкенд:** Python, FastAPI
- **Фронтенд:** Vue 3

## Skills и MCP

- Список и обоснование подключённых skills — см. [`SKILLS.md`](./SKILLS.md).
- **MCP: Playwright MCP.** Даёт агенту управление браузером (клики, ввод, скриншоты, чтение страницы) —
  используется, чтобы программно воспроизводить сценарии проверки фич A и B:
  - Фича A: отправить через UI выбор модельки/цвета (валидный и невалидный) и проверить, стартует ли гонка.
  - Фича B: инсценировать зависание/отсутствие реакции на кнопки и проверить, что показывается
    понятная ошибка по таймауту, а не бесконечная загрузка.
  Установка: пакет `@playwright/mcp` (или аналог), конфигурируется в `.mcp.json` проекта.

## Сценарий проекта (игровая механика)

1. Пользователь выбирает модельку машинки (из 3 предложенных вариантов) и её цвет.
2. После выбора машинка выходит на круговую трассу и едет, соревнуясь с другими машинками.

Это и есть «сопоставимый кусок своей системы»: вход от пользователя (выбор модели+цвета) →
валидация → запуск гонки (обращение к движку/логике гонки, который можно рассматривать
как «внешнюю зависимость», как LLM в примере с AI-review API).

## Фичи практики

### Фича A — входная валидация (экран выбора машинки)

**Принимаем на входе:**
- `model_id` — одна из 3 предложенных моделек (строго из разрешённого списка, не произвольная строка/число)
- `color` — цвет машинки (из заранее заданного набора допустимых цветов, см. палитру выше)

**Ожидаемое поведение:**
- Если `model_id` не входит в список из 3 моделек — запрос отклоняется, гонка не запускается.
- Если `color` не входит в разрешённый список — запрос отклоняется, гонка не запускается.
- Слишком большой/некорректный по формату запрос (лишние поля, битый JSON и т.п.) — отклоняется сразу.
- При любом отказе валидации — движок гонки НЕ запускается (не тратим ресурсы на старт заезда с мусорными данными).
- При успешной валидации — машинка с выбранными `model_id` и `color` выходит на трассу.

**Способ проверки:**
- Отправить корректный выбор (реальная модель из 3 + цвет из палитры) → гонка стартует.
- Отправить несуществующий `model_id` (например, 4-й, которого нет) → получить отказ, гонка НЕ стартует.
- Отправить цвет не из палитры → получить отказ.
- Отправить заведомо большой/испорченный запрос → получить отказ без запуска гонки.

### Фича B — ошибка зависимости (во время гонки)

**Контекст:** пока пользователь ещё только выбирает машинку (на экране выбора) — его не трогаем,
никаких проверок зависимости не делаем. Проверка нужна **после** того, как выбор сделан и гонка должна была начаться.

**Ожидаемое поведение:**
- Если после выбора машинки гонка зависла (машинка не выезжает на трассу в течение разумного времени) —
  система засекает это по таймауту и показывает понятную ошибку вместо бесконечной загрузки.
- Если во время гонки нажатия на кнопки управления ни к чему не приводят (машинка не реагирует/не едет) —
  система определяет, что отклика от движка гонки нет, и также показывает понятную ошибку
  (а не оставляет пользователя смотреть на зависший экран).
- Ограничивается время ожидания ответа от движка гонки (timeout), аналогично ограничению ожидания LLM в примере.
- Сценарии фичи A (валидация выбора) при этом продолжают работать как обычно — фича B их не ломает.

**Способ проверки:**
- Сценарий 1: выбор сделан корректно, гонка стартует и едет — ошибка НЕ показывается (ложных срабатываний нет).
- Сценарий 2: искусственно задержать/оборвать ответ движка гонки после выбора машинки → должна появиться
  понятная ошибка в течение заданного таймаута, а не бесконечное ожидание.
- Сценарий 3: во время гонки «отключить» реакцию на нажатия кнопок → система должна определить
  отсутствие отклика и показать ошибку, а не оставить машинку в зависшем состоянии без объяснения.

## Правила для агента

- Любое изменение — маленькое, проверяемое: diff → тест → commit.
- Перед реализацией — писать короткое, точное поручение (что именно изменить и зачем).
- Для фичи B — работать в отдельном worktree/контексте, не смешивать с веткой фичи A.
- После каждой фичи — review (в идеале subagent review) перед объединением.
- Стиль кода — согласно style guide проекта (см. раздел ниже, дополнять по мере появления правил).

## Тип и стиль сайта

Референс дизайна — лендинг в духе винтажного постера (пример: «Glizzy Store»):

- **Формат:** одностраничный лендинг (hero-секция на весь экран + скролл к контенту ниже).
- **Фон:** тёмный, насыщенный (тёмно-синий/тёмный нейтральный), контрастный с акцентами.
- **Акцентный цвет:** яркий тёплый (оранжевый/жёлтый), используется для типографики и крупной иллюстрации.
- **Типографика:** крупный, "ретро"/плакатный шрифт для названия/логотипа — главный визуальный акцент экрана.
- **Иллюстрация:** один крупный, стилизованный графический элемент по центру (в примере — хот-дог; у нас — тематика гонок: машина, трасса, флаг и т.п.), слегка "рукописный"/нарисованный стиль, не плоская иконка.
- **Минимализм в компоновке:** мало текста на первом экране — название, короткий подзаголовок, иконка/стрелка-индикатор скролла внизу справа.
- **Мелкие детали:** небольшая иконка/бейдж в углу (как логотип-печать), подпись/подзаголовок над основным логотипом.

Вывод: сайт — это яркий, стильный лендинг с сильным визуальным хиро-блоком, а не форма/дашборд. UI-работу стоит вести через `frontend-design` skill (есть в доступных) для вытягивания индивидуального, не шаблонного стиля.

## Цветовая палитра и тема — «Гонки»

Та же структура лендинга, что в референсе, но тема — гонки, а не еда, и цвета — фиолетово-голубые
(вместо тёмно-синего фона с оранжевым акцентом).

**Палитра (примерные hex, уточнять при вёрстке):**

| Роль                         | Цвет                  | Hex       |
|-------------------------------|------------------------|-----------|
| Фон (тёмный, основной)        | Глубокий фиолетовый    | `#1A1033` |
| Фон (альтернативный, темнее)  | Почти чёрный фиолетовый| `#0D0A1F` |
| Акцент 1 (главный, текст/лого)| Яркий фиолетовый       | `#8B5CF6` |
| Акцент 2 (доп., для градиента)| Голубой/циан           | `#22D3EE` |
| Акцент 3 (точечный, "искра")  | Неоново-розовый/лиловый| `#C084FC` |
| Текст на тёмном фоне          | Белый / светло-лиловый | `#F5F3FF` |

Можно сделать главный акцент как **градиент фиолетовый → голубой** (как неоновая подсветка трассы ночью) —
это будет аналог того, как в референсе крупный хот-дог нарисован поверх логотипа.

**Типографика:** крупный плакатный/спортивный шрифт для названия (похоже на referenced "Glizzy" —
широкие, немного скруглённые буквы), подзаголовок — более тонкий, с трек-кернингом (разрядкой), как "OLD VINTON".

**Иллюстрация вместо хот-дога (центральный элемент hero):**
- гоночный болид в движении (наклонно, с эффектом скорости/смаза), ИЛИ
- извилистая гоночная трасса сверху, ИЛИ
- шлагбаум/клетчатый флаг, пересекающий название сайта по диагонали (прямая замена композиции "хот-дог наискосок через текст").

**Прочее по аналогии с референсом:**
- небольшой круглый бейдж/эмблема в углу экрана (как звёздочка у Glizzy) — можно сделать в виде колеса/руля.
- стрелка-индикатор скролла внизу справа.
- короткий подзаголовок над названием (жанр/слоган), например что-то в духе "OLD VINTON" → тематическая строка про гонки.

## Style guide

**Бэкенд (Python/FastAPI):**
- Форматирование и линт — **Ruff** (`backend/pyproject.toml`). Запуск: `cd backend && ruff check . && ruff format .`
- Строки — двойные кавычки, длина строки — 100 символов.
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов и Pydantic-моделей/Enum.
- Входные данные API всегда описываются Pydantic-моделью с явным `extra="forbid"` —
  никаких "рыхлых" dict на входе эндпоинтов (см. `backend/app/models.py` как образец).
- Каждый публичный эндпоинт и модель — с коротким docstring, что он делает и почему (см. текущий код).

**Фронтенд (Vue 3):** следовать `vue-best-practices` (skill, см. `SKILLS.md`) — Composition API,
`<script setup>`, имена компонентов — `PascalCase`.

**Коммиты:** Conventional Commits — `feat:`, `fix:`, `docs:`, `test:`, `chore:` + короткое описание
на русском или английском (см. уже сделанные коммиты как образец).

**Правило для агента:** маленький diff → тест → commit. Не смешивать несколько фич в одном коммите.

## Автоматическая проверка (hooks)

Два разных hook'а, на двух разных уровнях:

### 1. Git pre-commit hook (`hooks/pre-commit`)

Срабатывает только в момент `git commit`. Устанавливается один раз через `bash hooks/install.sh`.
Прогоняет `ruff check` → `ruff format --check` → `pytest` и блокирует коммит при провале.

### 2. Hook агента (`.claude/settings.json`, `PostToolUse`)

Срабатывает **сразу после каждой правки файла агентом** (Edit/Write tool-call) —
не дожидаясь коммита. Запускает `scripts/check.sh` — детерминированный раннер
(ruff + pytest, без какой-либо LLM-оценки), результат (PASS/FAIL) возвращается агенту
прямо в его рабочий цикл.

```json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "bash scripts/check.sh" }] }
    ]
  }
}
```

**Проверено вручную:** `bash scripts/check.sh` — сначала отдельно (без hook, по инструкции),
затем цикл FAIL → PASS — намеренно сломан тест (ожидание неверного статус-кода) → скрипт
вернул `FAIL` с exit code 1 → тест возвращён в исходное состояние → скрипт вернул `PASS`
с exit code 0.

Итог: теперь агент узнаёт о сломанном коде сразу после своей же правки, а не только на
этапе коммита — это и есть "быстрая обратная связь", которую даёт hook уровня агента.
