# Design

## Context

Гонка рисуется на одном `<canvas>` 800x500 через Canvas 2D (`drawScene`, `drawCar` в
`frontend/src/App.vue`). Состояние машинок (`x`, `y`, `angle`) считает физика отдельно, рисование
только читает его. Трасса это овал `trackConfig` (`cx`, `cy`, `rx`, `ry`, `width`), финиш вверху.
Границы проверяются по радиальному смещению от центра (`keepInsideTrack`). Холст в разметке
находится в блоке состояния `racing` и появляется только при старте гонки, а блок обратного
отсчёта и блок победы это обычный HTML. Фронтенд-тестов нет, hook `scripts/check.sh` проверяет
только бэкенд. Мотивация: см. proposal.md, требования: см. specs.

## Goals / Non-Goals

**Goals:**
- Заменить только слой отрисовки, физика и состояние остаются нетронутыми.
- Вся 3D-логика в отдельном модуле, чтобы `App.vue` не разрастался.
- Один и тот же `canvas`, те же размеры и стили.

**Non-Goals:**
- Камера, которая двигается, переключение ракурсов.
- Модели из файлов, текстуры из картинок, постобработка.
- Фронтенд-тесты и их инфраструктура.

## Decisions

**1. Three.js и отдельный модуль сцены.**
Новый модуль в `frontend/src/` создаёт сцену из размеров трассы и холста и отдаёт три вещи:
отрисовать кадр по состоянию двух машинок, применить модель и цвет, уничтожить сцену.
`App.vue` вызывает его вместо `drawScene` и `drawCar`, а старый 2D-код удаляется. Альтернативы:
чистый WebGL (слишком много кода), Canvas 2D с псевдообъёмом (не даёт настоящего 3D, о чём
договорились).

**2. Рендерер привязывается к существующему `canvas`.**
Размер 800x500 и класс `race-canvas` сохраняются. Один холст не может работать одновременно в
2D и WebGL, поэтому вызов `getContext("2d")` исчезает полностью. Плотность пикселей ограничивается
двойкой, чтобы не нагружать ретина-экраны.

**3. Соответствие координат физики и 3D.**
Единица мира равна одному пикселю прежнего холста, центр трассы переносится в начало координат.
Игровое `x` превращается в мировое `x - cx`, игровое `y` в мировое `z - cy` (ось вниз экрана
становится осью к камере), поворот вокруг вертикальной оси равен `-angle`. Так направление
движения машинки и её нос в 3D совпадают с физикой, и физику менять не нужно.

**4. Камера.**
Перспективная, неподвижная, смотрит в центр трассы, наклон вниз 45-55 градусов. Высота и
расстояние подбираются так, чтобы внешний контур трассы (`rx + width/2` на `ry + width/2`)
помещался в кадр с небольшим запасом при соотношении 800:500. Точные числа подбираются при
реализации и фиксируются константами.

**5. Трасса строится из тех же параметров.**
Дорога это плоская лента между контурами бордюров, которые, как и в прежней 2D-отрисовке,
задаются эллипсами `rx ± width/2` на `ry ± width/2`. Так между дорогой и бордюрами нет щелей.
Бордюры это невысокие полосы: внешний фиолетовый (`#8B5CF6`) и внутренний голубой (`#22D3EE`),
как раньше. Осевая линия пунктирная, линия старта и финиша клетчатая, в том же месте (вверху,
по центру). Цвета фона и дороги берутся из `AGENTS.md`.

**6. Машинки из простых форм, параметры по моделям.**
Каждая машинка это группа: корпус, кабина, четыре колеса, две фары. Для трёх моделей
(`racer`, `drifter`, `tank`) задаётся набор пропорций (длина, ширина, высота корпуса, высота и
положение кабины, радиус колёс). Спорткар низкий и длинный, Дрифтер шире, Внедорожник выше и с
большими колёсами. Размеры по основанию близки к прежним 32x18, а для читаемости объёма вся машинка визуально
увеличена в 1,25 раза (физика и границы не меняются). Цвет корпуса из выбранного цвета палитры, кабина тёмная, фары жёлтые.

**7. Свет и тень.**
Мягкий общий свет и один направленный источник сбоку-сверху с тенью. Машинки отбрасывают тень,
трасса принимает её. Область теней ограничивается размерами трассы, чтобы тень была чёткой.

**8. Подпись игрока как спрайт.**
Надпись P1/P2 это плоский объект, который всегда повёрнут к камере и висит над машинкой. Так
она горизонтальна на любом повороте, и не нужно пересчитывать позицию в экранных координатах.

**9. Жизненный цикл.**
Холст появляется только в состоянии `racing`, поэтому сцена создаётся при первом кадре, когда
`canvasRef` уже есть, и уничтожается (освобождаются геометрии, материалы, рендерер) при выходе
из `racing` и при размонтировании, чтобы повторные запуски не копили WebGL-контексты.

**10. Недоступное 3D.**
Если создать рендерер не получилось, показывается понятное сообщение вместо поля, остальной
интерфейс работает.

## Risks / Trade-offs

- [Размер сборки вырастет из-за `three`] → импортировать только нужные части, проверить размер
  после `npm run build`.
- [Расхождение положения машинки у бордюра на экране и в логике (`keepInsideTrack` радиальный,
  дорога строится по нормали)] → сверить визуально на всех участках овала, при заметном
  расхождении подправить отрисовку ленты, а не физику.
- [Мало света: машинки выглядят плоско] → подобрать соотношение общего и направленного света на
  реальной гонке.
- [Нет автотестов фронтенда] → ручная проверка по сценариям из specs со скриншотами и
  `npm run build`, перед приёмкой показать их человеку.
- [Утечка WebGL при перезапусках] → явное освобождение ресурсов, проверка пятью подряд запусками.

## Migration Plan

Миграции данных нет. Изменение только во фронтенде, откат через `git revert` коммита или
отдельных коммитов. Пока 3D не принят, старая 2D-отрисовка остаётся в истории git.

## Open Questions

- Нужна ли в проекте простая автоматическая проверка фронтенда (например, тест функции перевода
  координат) или достаточно ручной проверки. Ответ не меняет ни specs, ни подход, можно решить
  при реализации.
