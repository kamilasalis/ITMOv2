# Гонки Constitution

## Core Principles

### I. Фиксированный стек: FastAPI + Vue 3

- Бэкенд MUST быть реализован на FastAPI (Python, `backend/`); фронтенд MUST быть
  реализован на Vue 3 (`frontend/`, Composition API, `<script setup>`).
- Агент и разработчики MUST NOT добавлять новые фреймворки (веб-, UI-, state-management-,
  ORM-, тестовые фреймворки и т. п.) ни в бэкенд, ни во фронтенд.
- Добавление любой новой зависимости в `backend/requirements.txt`, `backend/pyproject.toml`
  или `frontend/package.json` MUST быть явно указано в плане фичи с обоснованием; если
  зависимость по сути является фреймворком — она запрещена без поправки к конституции.

**Обоснование**: единый небольшой стек снижает сложность, сохраняет воспроизводимость
проверок и не даёт агенту «решать задачу заменой инструментов».

### II. Неприкосновенность физики и управления

- Физика машинок (ускорение, торможение, трение, максимальная скорость, скорость
  поворота, обработка столкновений — `updatePhysics()` и параметры моделей в
  `frontend/src/App.vue`) MUST NOT изменяться без отдельного явного согласования с
  человеком.
- Управление (раскладка клавиш: игрок 1 — `W/A/S/D`, игрок 2 — стрелки; логика
  обработки нажатий) MUST NOT изменяться без отдельного явного согласования.
- Согласование MUST быть зафиксировано в спеке фичи (раздел Clarifications или
  требование), прежде чем начнётся реализация. Фича, не касающаяся физики/управления,
  MUST оставлять их поведение побайтово-эквивалентным по результату.

**Обоснование**: ощущение от игры — ядро продукта; незаметные правки чисел ломают
баланс моделей `racer` / `drifter` / `tank`.

### III. Зелёный scripts/check.sh (NON-NEGOTIABLE)

- Единственный источник истины о качестве — `bash scripts/check.sh`
  (ruff check, ruff format --check, pytest).
- Любое изменение MUST завершаться с `PASS` от `scripts/check.sh` до того, как задача
  считается выполненной.
- Запрещено обходить проверку: отключать правила ruff, помечать тесты `skip`/`xfail`,
  удалять тесты или ослаблять `check.sh` без отдельного согласования с человеком.

**Обоснование**: детерминированный runner даёт одинаковый результат для одинакового кода
и не зависит от субъективной LLM-оценки.

### IV. Требования как сценарии Given/When/Then

- Каждое функциональное требование в спеке MUST сопровождаться минимум одним проверяемым
  сценарием в формате **Given** (исходное состояние) / **When** (действие) / **Then**
  (наблюдаемый результат).
- Сценарий MUST быть конкретным и проверяемым: в Then — наблюдаемое значение, статус,
  текст или состояние UI, а не формулировки вида «работает корректно» / «удобно».
- Требование без сценария считается неполным: план и задачи по нему MUST NOT
  создаваться до его дополнения.
- Для бэкенда сценарии SHOULD отображаться в pytest-тесты, запускаемые через
  `scripts/check.sh`.

**Обоснование**: проверяемые сценарии делают спеку контрактом и позволяют однозначно
определить, выполнено ли требование.

### V. Человек решает то, чего нет в спеке

- Если для реализации нужно решение, не зафиксированное в спеке, плане или этой
  конституции, агент MUST остановиться и задать вопрос человеку.
- Агент MUST NOT выбирать вариант самостоятельно, «по умолчанию» или «как разумнее»,
  даже если вариант кажется очевидным.
- Ответ человека MUST быть внесён в спеку (раздел Clarifications или соответствующее
  требование со сценарием Given/When/Then) до продолжения реализации.

**Обоснование**: неявные решения агента расходятся с ожиданиями и не оставляют следа;
фиксация в спеке сохраняет историю решений.

## Технические ограничения

- Бэкенд: FastAPI, валидация входных данных — Pydantic с `extra="forbid"`.
- Фронтенд: Vue 3 Composition API (`<script setup>`), сборка Vite.
- Допустимые модели машинок: `racer`, `drifter`, `tank`; допустимые цвета — пастельная
  палитра (`red`, `yellow`, `purple`). Расширение этих списков — изменение, требующее
  спеки со сценариями.
- Линтер и формат бэкенда — ruff; тесты — pytest (`backend/tests/`).

## Процесс разработки

1. Спека (`/speckit-specify`) — требования со сценариями Given/When/Then (Принцип IV).
2. Уточнения (`/speckit-clarify`) — все открытые решения закрываются человеком (Принцип V).
3. План и задачи (`/speckit-plan`, `/speckit-tasks`) — Constitution Check: стек
   (Принцип I), затрагивание физики/управления (Принцип II).
4. Реализация (`/speckit-implement`) — после каждого шага `bash scripts/check.sh` → `PASS`
   (Принцип III).
5. Ревью — проверка соответствия всем принципам; нарушения без согласования блокируют
   слияние.

## Governance

- Конституция имеет приоритет над остальными практиками и инструкциями агента в этом
  проекте.
- Поправки вносятся только человеком (или агентом по явному поручению человека) через
  `/speckit-constitution` с Sync Impact Report.
- Версионирование — SemVer: MAJOR — удаление или переопределение принципа; MINOR —
  новый принцип/раздел или существенное расширение; PATCH — уточнения формулировок.
- Каждый план (`plan.md`) MUST содержать Constitution Check; каждое ревью MUST
  проверять соответствие принципам I–V.
