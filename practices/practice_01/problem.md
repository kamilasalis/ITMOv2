# Проблема и метрики

## Проблема

- Пользователь: инженер-ревьюер и разработчик PR.
- Ситуация: разработчик открывает PR, а ревьюер тратит время на ручной поиск типичных синтаксических ошибок, уязвимостей и нарушения базовых контрактов API.
- Что происходит сейчас: первичная автоматизация в PR (TRAINING_PR.diff) работает нестабильно: принимает невалидированный payload без проверки ключа `diff`, не фильтрует секреты (SEC-1), не проверяет лимит размера в 20 000 символов (API-1), падает с 500 при таймаутах LLM и возвращает сырой неструктурированный комментарий вместо формата OUT-1.
- Почему это мешает пользователю или бизнесу: ревьюер не может доверять сервису из-за падений и шума, вынужден вручную дублировать рутинные проверки, что увеличивает Time to Review и отвлекает от архитектурного анализа.
- Что не входит в задачу: автоматический мерж или отклонение PR в VCS, автоматическое исправление исходного кода, замена архитектурного ревью человеком.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля успешных ответов API (2xx) на валидные diff | 0% (сервис в PR падает при непредвиденных форматах и не имеет таймаута) | >= 99% | При каждом запуске интеграционных тестов и на продовой телеметрии | Логи API (`OBS-1`), мониторинг |
| Доля структурированных ответов по контракту OUT-1 | 0% (возвращается только неструктурированный dict `{"comment": "..."}`) | 100% ответов содержат `summary`, `<=3 risks`, `checks` | На каждом ответе LLM-сервиса | Тесты контракта API |
| Доля утечек секретов в промпт LLM | 100% при наличии токена в diff (нет санитайзера SEC-1) | 0% (все токены маскируются на `[REDACTED]`) | В CI перед обращением к внешнему LLM | Security integration tests |

## Почему изменение метрики подтвердит решение проблемы

Выполнение этих метрик гарантирует, что сервис работает стабильно, безопасно передает данные во внешний LLM и выдает ревьюеру компактную, структурированную и доказательную сводку рисков, которую можно сразу проверить без рутинного ручного анализа.

- Для чего: формулирование измеримых метрик качества работы API и безопасности.
- Тип промпта: master prompt (P1-02).
- Строка в [`prompts.md`](prompts.md): строка P1-02.
- Что проверили и исправили сами: убрали абстрактные метрики вроде CSAT/ROI, оставили проверяемые инженерные показатели, привязанные к правилам SEC-1, API-1 и OUT-1.
