Ниже — обзор проблем в TRAINING_PR.diff, отсортированный по серьёзности, с указанием мест в диффе.
Критичные
- app/api.py (стр. 35–38) — KeyError при отсутствии поля diff. В create_review используется payload["diff"] без валидации. Если ключа нет или он не строка, будет 500 вместо ожидаемого 422. Решение: описать тело запроса через Pydantic-модель (например, ReviewRequest(diff: str)) или как минимум проверять наличие ключа и тип и возвращать 422 через HTTPException.
- app/review_service.py (стр. 19–22) и app/api.py (стр. 36–38, 40–42) — несовместимость с Python < 3.9 из-за аннотаций dict[str, str]. Если в проекте не зафиксирован min Python 3.9+, это SyntaxError. Решение: либо зафиксировать Python ≥3.9, либо заменить на Dict[str, str] из typing.
- app/api.py (стр. 35–38) — отсутствие схемы ответа и валидации. Возврат «сырого» словаря без response_model приводит к нефиксированной схеме API и ухудшает контракт. Решение: ввести Pydantic-модель ответа либо TypedDict, и указать response_model.
Серьёзные
- app/api.py (стр. 35–38) — отсутствие обработки ошибок LLM/сервиса. Любое исключение из review_service.review/llm.generate даст 500. Желательно перехватывать исключения и возвращать контролируемые ошибки (например, 502/500 с сообщением), чтобы клиенту было ясно, что произошло.
- app/api.py (стр. 35–38) — отсутствие ограничений на размер входа. Поле diff может быть большим; без ограничений это риск по памяти/времени. Следует продумать лимиты или хотя бы защиту на уровне API/LLM.
- app/api.py (стр. 35–38) — типизация payload: dict слишком общая. FastAPI подставит тело как dict, но нет контракта и документации в OpenAPI. Это ухудшает DX и тестируемость. Решение: Pydantic-модель запроса.
- app/review_service.py (стр. 19–22) — нет нормализации/санитизации входного diff. Передача диффа напрямую в LLM увеличивает риск prompt injection и утечек внутренних инструкций. Хотя это часто допустимо, стоит хотя бы ограничить/фильтровать/обрезать ввод и/или добавить системные инструкции.
Средние/минорные
- app/review_service.py (стр. 10–13) — косметическая перестановка сигнатуры LLM.generate с однострочного ... на многострочный ... без функциональной пользы. Это «шумиха» в PR без добавленной ценности.
- app/api.py (стр. 35–38) — отсутствие явной документации эндпойнта: нет описаний, примерного запроса/ответа, тегов. В OpenAPI будет труднее ориентироваться.
- app/api.py (стр. 35–38) — отсутствие аутентификации/авторизации. Возможно так и задумано, но если сервис публичный, это риск злоупотреблений.
- app/api.py (стр. 40–42) — health тоже использует dict[str, str], что тянет ту же совместимость с Python <3.9.
- Общие тесты — отсутствуют. Нет юнит-тестов на ReviewService.review и интеграционных/endpoint-тестов на /api/reviews.
Открытые вопросы
- Какая минимальная версия Python поддерживается проектом? Если <3.9, потребуется заменить аннотации на типы из typing.
- Что именно возвращаем клиенту: только один «comment» или предполагается расширить схему (например, список замечаний, уровни серьёзности, ссылки на строки)?
- Нужна ли авторизация/квотирование на /api/reviews? Какой ожидается размер diff и SLA по времени ответа?
- Где и как создаётся review_service (в app/dependencies)? Есть ли зависимости/инициализация LLM, таймауты, ретраи?
Краткое резюме изменений
1. Ввести Pydantic-модель запроса ReviewRequest(diff: str) и ответа; добавить response_model в роут.
2. Обработать отсутствие поля diff и неверные типы: возвращать 422.
3. Добавить перехват исключений от LLM и маппинг на HTTP-ошибки.
4. Зафиксировать min Python ≥3.9 или перейти на typing.Dict и др. из typing.
5. Продумать ограничения на размер и формат diff и добавить базовую защиту от злоупотреблений.
6. Добавить тесты: юнит на ReviewService, интеграционный на /api/reviews.
