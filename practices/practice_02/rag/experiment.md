## Ответ со ссылками на источники

### 1. Выбор метрик: почему перцентили (p95/p99), а не среднее значение
- **Теоретическое обоснование:** Согласно [общепринятая методология нагрузочного тестирования], среднее арифметическое время ответа (avg duration) скрывает единичные длительные «хвосты» и выбросы задержек (long tail latency). При тестировании систем с внешними блокирующими вызовами даже при среднем времени 2 секунды 5% пользователей могут получать таймаут или зависание. Использование перцентилей $p(95)$ или $p(99)$ гарантирует, что 95% или 99% запросов укладываются в установленный SLA, делая оценку надежности строгой и нечувствительной к сглаживанию выбросов.
- **Синтаксис задания порогов в k6:** Согласно [k6 docs: Thresholds], формальное задание условий успешности теста, приводящих к падению сценария при их превышении (exit code != 0), оформляется через массив условий в объекте `thresholds`:
  ```javascript
  export const options = {
    thresholds: {
      'http_req_duration': ['p(95)<10500'], // p95 времени ответа строго меньше порога
      'http_req_failed': ['rate<0.01'],    // процент ошибок менее 1%
    },
  };
  ```

### 2. Обоснование конкретных чисел для `tests_load.md` сервиса
- **Порог для эндпоинта `POST /api/reviews` (10.5 с):**
  - Правило `REL-1` ([practices/practice_01/context.md, раздел «Факты и правила»]; [practices/practice_01/CASE.md, раздел «Правила репозитория»]) гласит: *«внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ»*.
  - В проекте уже есть прецедент фиксации границы и допуска: в [practices/practice_01/tests_integration.md, строка про mock LLM с задержкой 15с → 504] зафиксировано требование: *«Срабатывание таймаута на 10-й секунде (REL-1) и возврат контролируемой ошибки 504. Замер длительности вызова <= 10.5с и статус 504»*.
  - Таким образом, числовой порог времени ответа формируется как 10 секунд (лимит таймаута по REL-1) + 0.5 секунды (допуск на внутреннюю обработку FastAPI и сериализацию/десериализацию), что дает порог `http_req_duration: ['p(95)<10500']`.
- **Порог размера тела запроса и отсечки (20 000 символов и возврат HTTP 413):**
  - Правило `API-1` ([practices/practice_01/context.md, раздел «Факты и правила»]; [practices/practice_01/CASE.md, раздел «Правила репозитория»]) требует: *«diff длиннее 20 000 символов отклоняется с HTTP 413»*.
  - В сценарии стресс-теста отсечки валидация diff длиной 25 000 символов ([practices/practice_01/tests_integration.md, строка «FastAPI <-> Лимит API-1»]) должна возвращать HTTP 413 мгновенно (до передачи во внешний LLM), удерживая порог `p(99) < 50ms`.
- **Эндпоинт `GET /health` (`p99 < 20ms`):**
  - В [practices/practice_01/TRAINING_PR.diff, app/api.py] эндпоинт `/health` возвращает статический словарь `{"status": "ok"}` без обращения к сервисам и базе данных. Порог 20 мс при 100 RPS обусловлен отсутствием I/O операций.
- **Ограничения по потреблению RAM и CPU:**
  - **Источника нет:** В файлах `context.md`, `CASE.md` и `TRAINING_PR.diff` конкретные лимиты утилизации CPU (в процентах) и RAM (в мегабайтах) отсутствуют. Поэтому в нагрузочных тестах измеряется общая стабильность процесса (отсутствие деградации, утечек памяти и аварийных завершений по OOM), но конкретные числа утилизации ресурсов не заявляются как проектные нормативы.
