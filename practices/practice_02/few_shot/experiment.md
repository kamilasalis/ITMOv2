# Few-shot

- Артефакт Практики 1: tests_load.md
- Что хотим улучшить:
Добавить рабочий скрипт нагрузки (файл k6 load_test.js или сценарий Locust) с командой запуска.
Явно зафиксировать, что LLM в нагрузочных тестах подменяется моком.
Обосновать пороги (p99<20мс, 12с) — указать железо/окружение и число воркеров Uvicorn.
Добавить сценарий деградации — поведение сервиса при параллельных запросах и медленном ответе LLM (близко к таймауту REL-1).
Добавить системные метрики — потребление RAM и CPU при больших diff.
## Примеры

### Хороший результат
Сценарий: Потоковая отправка валидных diff
Окружение: FastAPI/uvicorn, 4 воркера, 1 CPU / 2GB RAM (локальный тест)
LLM: замокан фикстурой с фиксированной задержкой 200мс — реальный провайдер не вызывается
Нагрузка: 10 одновременных пользователей, diff 5 000 символов, 120 секунд
Допустимый предел: p95 < 10.5с (REL-1: таймаут LLM 10с + запас на обработку), 0% ошибок 5xx
Деградация: если mock-LLM отвечает дольше 10с, сервис возвращает 504 и не блокирует остальные воркеры — проверяется отдельным прогоном с задержкой 11с
Системные метрики: RSS памяти процесса и CPU% на пике нагрузки
Evidence: load/diff_review.js (k6-скрипт), команда k6 run load/diff_review.js, JSON-отчёт k6 run --out json=result.json

### Плохой результат
Сценарий: Потоковая отправка валидных diff
Допустимый предел: 12 секунд
Evidence: Отчет locust

## Запрос
Ты работаешь с артефактом tests_load.md (нагрузочные проверки сервиса ревью PR из TRAINING_PR.diff). Перепиши файл, устранив 5 проблем: (1) нет рабочего скрипта нагрузки и команды запуска; (2) не указано, мокается ли LLM; (3) пороги (p99<20мс, 12с) ничем не обоснованы — нет данных об окружении и числе воркеров; (4) нет сценария деградации при параллельной нагрузке и медленном ответе LLM; (5) не измеряются RAM и CPU.

Следуй формату из примера «Хороший результат» и не повторяй формат «Плохой результат». Используй только правила из context.md (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1) — не придумывай новых правил и не меняй уже согласованные пороги REL-1 (10с) и API-1 (20 000 символов) без основания. Для каждого сценария из исходной таблицы добавь: конкретный скрипт/команду запуска, явное указание про мок LLM, обоснование порога, отдельный сценарий деградации, системные метрики.

Верни обновлённый tests_load.md целиком, сохранив структуру файла (таблица + абзац об ограничениях MVP + раздел «Как использовали AI» со ссылкой на нужную строку в prompts.md).

## Что получили

Модель успешно сгенерировала обновленный документ нагрузочного тестирования, закрыв все 5 выявленных дефектов:
1. **Рабочие скрипты и запуск:** сформирован k6-скрипт (`load/diff_review.js`) с проверками кодов ответов, порогов и параметризацией задержки через переменную `MOCK_LATENCY`, а также приведены точные команды запуска штатного теста и сценария деградации.
2. **Мокирование LLM:** для всех сценариев явно зафиксировано мокирование LLM (фикстура с задержкой 200 мс для эмуляции I/O, исключающая реальные сетевые вызовы и списание токенов) или полное отсутствие обращений к LLM (`/health`, `API-1`).
3. **Обоснование порогов и окружение:** специфицировано окружение выполнения (FastAPI/Uvicorn, 4 воркера, 1 vCPU / 2GB RAM); пороги согласованы с правилами `context.md` (p95 < 10.5 с на базе `REL-1` таймаута в 10 с, p99 < 50 мс для ранней отсечки `API-1`, p99 < 20 мс для in-memory `/health`).
4. **Сценарий деградации:** описано и закодировано поведение сервиса при зависании mock-LLM на 11 с — сервис отсекает запрос по таймауту `REL-1` (10 с) с кодом 504 / fail-safe, предотвращая зависание и блокировку остальных воркеров.
5. **Системные метрики:** для каждого сценария добавлены конкретные требования по мониторингу утилизации CPU% и лимитам потребления RSS-памяти процесса под нагрузкой.
